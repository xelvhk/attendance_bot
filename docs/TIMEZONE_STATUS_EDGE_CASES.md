# Attendance Bot — Timezone / Status Edge Cases

Дата: `2026-04-30`

## Цель

Собрать граничные сценарии для переходов статусов посещаемости с учетом часовых поясов пользователя.

## Базовые инварианты

1. Все события хранятся в UTC, показываются в timezone пользователя.
2. Определение "сегодня/вчера/неделя" делается в timezone пользователя, не сервера.
3. Смена timezone не должна ломать историю и дублировать статусы.

## Edge-cases: Timezone

1. Пользователь меняет timezone в середине дня:
- Был `Europe/Moscow`, стал `Asia/Almaty`.
- Ожидаемо: текущий day-bucket пересчитывается по новому timezone только для отображения, данные не дублируются.

2. Сдвиг даты при UTC-конвертации:
- Локально `00:15`, в UTC это предыдущий день.
- Ожидаемо: статус идет в локальный день пользователя.

3. Отрицательные UTC-offset (например, `America/New_York`):
- Проверить корректность "сегодня" и "вчера" при вечерних отметках.

4. Невалидный timezone в профиле:
- Ожидаемо: fallback на безопасный timezone по умолчанию + предупреждение в лог.

## Edge-cases: DST (летнее/зимнее время)

1. День с 23 часами (переход на летнее время):
- Проверить, что окно отметки не "пропадает".

2. День с 25 часами (переход на зимнее время):
- Проверить отсутствие двойной записи в повторяющийся час.

3. Отметка в "не существующее локальное время":
- Ожидаемо: нормализация к ближайшему валидному времени или блок с понятной ошибкой.

## Edge-cases: Status transitions

1. Повторный same-status submit:
- `present -> present`.
- Ожидаемо: идемпотентность, без дублирования строки.

2. Конфликтные статусы в одном слоте:
- `present -> late` через короткий интервал.
- Ожидаемо: детерминированное правило приоритета или последнее подтвержденное действие.

3. Редактирование прошлого дня:
- Проверить права и аудит.

4. Параллельные запросы (гонка):
- Два клиента отправляют разные статусы почти одновременно.
- Ожидаемо: транзакционная консистентность, predictable winner-rule.

5. Backfill после офлайн-периода:
- Клиент присылает события "задним числом".
- Ожидаемо: корректный mapping в локальные дни и явная пометка источника.

## Edge-cases: Reporting/Stats

1. Неделя пересекает границы месяца/года.
2. Пользователь сменил timezone в середине недели.
3. Агрегация не должна терять или дублировать день на DST.

## Минимальный regression-checklist

1. UTC↔local roundtrip для `today/yesterday`.
2. DST spring/fall сценарии на test fixtures.
3. Idempotency тесты для same-status.
4. Race-condition тест для конкурентного обновления.
5. Повторная проверка недельной статистики после смены timezone.
